# How to Verify with FossID

#### 1. FossID Verification Process Overview

* The FossID verification is conducted through a **9-step workflow**. You can monitor the current progress directly on the workflow bar.
* Developers can proceed through the stages alongside the Manager.
* The Manager has the authority to perform all stages independently.
* Verification Flow: Scan → Identification → Usage Type Input → Review → Follow-up → Completion
* You can check the current stage on the workflow bar.

<div align="left"><figure><img src="../../.gitbook/assets/image (2).png" alt="" width="563"><figcaption></figcaption></figure></div>

#### 2. Requesting Verification (Scanning)

Click on **\[FossID Verification]** to select the files you wish to verify.

<div align="left"><figure><img src="../../.gitbook/assets/image (15).png" alt="" width="552"><figcaption></figcaption></figure></div>



In the **FossID Verification Request** window, configure the following items:

<div align="left"><figure><img src="../../.gitbook/assets/image (16).png" alt="" width="338"><figcaption></figcaption></figure></div>

* **Import Method**:
  * Repository: You can perform verification by entering the repository address.
  * Upload file: You can request verification by uploading local files.
* **Request Message**: You can enter a request message when submitting the verification request.



When you click the **\[Request]** button, the file analysis begins through the FossID tool. Once the analysis is complete, the verification process will proceed.

#### (4). Scanned Component List

* Displays the list of scanned components, and you can click on each item to check the detailed information.

<div align="left"><figure><img src="../../.gitbook/assets/clarity_section_yellow_4 (1).png" alt=""><figcaption></figcaption></figure></div>

**Item Description**

* CONFLICT: Displayed in red if the component conflicts with the license policy, and in white if there are no conflicts.
* COMPONENT (COMPONENT VERSION) : Information on the component name and its version.
* COMPONENT LICENSE: License information for the component.
* OBLIGATION TYPE:  Information on the obligation type for the license (based on the project's license policy).
* USAGE TYPE : The default value is N/A; it can be specified during the Usage Type Input stage.
* DISCLOSE:  Indicates whether the component's source code is disclosed.
* MODIFICATION: Indicates whether the component has been modified.
* NOTICE: Indicates whether a notice is required for the component.
* PATENT: Indicates whether there are patents related to the component.
* VULNERABLE LEVEL: The security vulnerability grade (based on the project's security vulnerability policy).
* SEVERITY: The risk level of the vulnerability based on the CVSS score.
* SECURITY: Displays a list of CVEs (security vulnerabilities) found in the component.

#### 4. Detailed Description of the FossID Verification Workflow

* The following explains each of the 9 stages.



**Step1 - Analyzing**

* The file scanning process is in progress in the background.
* Once the scan is complete, the system automatically proceeds to the Request Usage Type Review stage.

<div align="left"><figure><img src="../../.gitbook/assets/image (161).png" alt="" width="563"><figcaption></figcaption></figure></div>



**Step 2 – Analysis Check**

* When the scan status reaches Success, the analysis is complete, and you can proceed with the verification workflow.

<div align="left"><figure><img src="../../.gitbook/assets/image (162).png" alt="" width="563"><figcaption></figcaption></figure></div>



* This is the stage where the Developer requests verification from the Manager.
* This screen is displayed to the Developer after the scan is complete.

<div align="left"><figure><img src="../../.gitbook/assets/image (164).png" alt="" width="563"><figcaption></figcaption></figure></div>



* The Developer can click the \[Add new comment] button to leave a comment for the current stage.

<div align="left"><figure><img src="../../.gitbook/assets/image (181).png" alt="" width="563"><figcaption></figcaption></figure></div>



* Input the message to be sent to the Manager in this field.

<div align="left"><figure><img src="../../.gitbook/assets/image (182).png" alt="" width="407"><figcaption></figcaption></figure></div>



* You can check the comments left for the current stage in the Communication section.

<div align="left"><figure><img src="../../.gitbook/assets/image (183).png" alt="" width="563"><figcaption></figcaption></figure></div>



**Step 3 – Load Identification Results**

* This stage involves performing the FossID verification and loading the results.
* The Manager can proceed with the FossID verification using two methods

<div align="left"><figure><img src="../../.gitbook/assets/image (165).png" alt="" width="563"><figcaption></figcaption></figure></div>



**Step 3.1 - Two Methods for FossID Verification**

1. The Manager performs the verification directly on the FossID site.

<details>

1. Click the \[Open FossID Site] button in Step 3 of the image to navigate to the internal FossID site URL.([Refer to the Internal FossID URL Configuration Method](../../manager-guide/preferences/server-and-service-integration-settings.md#id-2.-fossid))



2. Log in to FossID on the login screen.

<div align="left"><figure><img src="../../.gitbook/assets/image (10).png" alt="" width="563"><figcaption></figcaption></figure></div>

<div align="left"><figure><img src="../../.gitbook/assets/image (11).png" alt="" width="563"><figcaption></figcaption></figure></div>



4. Search by the CSC **Project ID** to display the iteration list for that project. Select the specific iteration you wish to verify.

<div align="left"><figure><img src="../../.gitbook/assets/image (12).png" alt="" width="563"><figcaption></figcaption></figure></div>



5. On this screen, you can review the list of detected components and manually select the ones to apply.
   1. Click All Files (No. 1) and click the icon (No. 2) for the component you wish to apply from the detected list.
   2. Click \[Identify files matching linux] (No. 3) to open the pop-up window.

<div align="left"><figure><img src="../../.gitbook/assets/image (13).png" alt="" width="563"><figcaption></figcaption></figure></div>



6. Apply the components used from the detected list by clicking the \[Apply] button.

<div align="left"><figure><img src="../../.gitbook/assets/image (8).png" alt=""><figcaption></figcaption></figure></div>



7. Once the verification in FossID is complete, return to the CSC and click the \[Load Identification Results] button to import the verification results.

<div align="left"><figure><img src="../../.gitbook/assets/image (166).png" alt="" width="563"><figcaption></figcaption></figure></div>



8. In the next stage, you can verify that the list of applied components is correctly reflected in the Component List.

**Step 5 – Usage Type Input**

* This is the stage where the Developer enters the usage type.
* The Developer can leave a comment regarding the current stage.

<div align="left"><figure><img src="../../.gitbook/assets/image (173).png" alt="" width="563"><figcaption></figcaption></figure></div>



* The Developer inputs how each component is being used. Depending on the selected usage type, license policy conflicts may be resolved or new conflicts may arise. ([Refer to the COMPONENT LIST description](how-to-verify-with-fossid.md#id-4-.-component-list))

<div align="left"><figure><img src="../../.gitbook/assets/image (93).png" alt="" width="563"><figcaption></figcaption></figure></div>



* Exception license policy rules based on the combination type can be configured in the License Policy Rules Exception List.

**Step 6 –  Review**

* This is the stage where the Manager reviews the entered Usage Types and any components with conflicts. This stage cannot be performed by the Developer.
* If there are no issues, move to the **Ready** state to complete the verification.
* f further review is required, instruct to perform **Follow-up** actions.
* If re-verification is needed, click the **Re-verify** button to perform a scan.
* If the request needs to be rejected, click the **Reject** button to return to the previous stage.

<div align="left"><figure><img src="../../.gitbook/assets/image (177).png" alt="" width="563"><figcaption></figcaption></figure></div>



* The Manager can enter compliance conditions for components where conflicts have occurred.

<div align="left"><figure><img src="../../.gitbook/assets/image (97).png" alt="" width="563"><figcaption></figcaption></figure></div>



**Step 7 - Follow-up**

* This is the stage where the Developer checks the compliance conditions left by the Manager and marks whether they have been fulfilled.
* The Developer can leave a comment regarding the current stage.

<div align="left"><figure><img src="../../.gitbook/assets/image (178).png" alt="" width="563"><figcaption></figcaption></figure></div>



* After checking the fulfillment status, the Developer completes the follow-up actions.

<div align="left"><figure><img src="../../.gitbook/assets/image (136).png" alt="" width="563"><figcaption></figcaption></figure></div>



**Step 8 - Check follow-up**

* This is the stage where the Manager reviews the compliance status checked by the Developer. This stage cannot be performed by the Developer.
* If there are no issues, move to the **Ready** state to complete the verification.
* If re-verification is required, click the **Re-verify** button to perform a re-scan.
* If the request needs to be rejected, click the **Reject** button to return to the previous stage.

<div align="left"><figure><img src="../../.gitbook/assets/image (179).png" alt="" width="563"><figcaption></figcaption></figure></div>



**Step 9 - Ready**

* Verification Completed State
* [An SBOM can be generated based on the verification results.](how-to-verify-with-fossid.md#id-5-.-verification-report) (Available from Step 4 onwards)
* You can review all Communications from the entire verification process.
* Click the \[Revoke Verification] button to cancel the completed status and return to a previous state.
