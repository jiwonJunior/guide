# How to Verify with Clarity

#### 1. Clarity Verification Process Overview

* Clarity verification proceeds through an **8-stage workflow**.
* Developers can proceed together with the Administrator.
* The Administrator can perform all stages independently.
* Verification Flow: Scan → Usage Type Input → Review → Follow-up → Completed
* The current stage can be checked on the workflow bar.

<div align="left"><figure><img src="../../.gitbook/assets/image (100).png" alt="" width="563"><figcaption></figcaption></figure></div>



#### 2. How to Request Verification (Scan)

Click \[Clarity Verification] and select the file to be verified.

<div align="left"><figure><img src="../../.gitbook/assets/image (51).png" alt="" width="563"><figcaption></figcaption></figure></div>



Configure the following items in the **Clarity Verification Request** window

<div align="left"><figure><img src="../../.gitbook/assets/image (14).png" alt="" width="338"><figcaption></figcaption></figure></div>

* **Import Method**:
  * Repository: You can verify by entering the repository address.
  * Upload file: You can request verification by uploading a local file.
* **Request Message**: You can enter a request message when requesting verification.



Click the \[Request] button to start the file analysis through the Clarity tool. Once the analysis is complete, the verification process will proceed.

<div align="left"><figure><img src="../../.gitbook/assets/image (55).png" alt="" width="563"><figcaption></figcaption></figure></div>

* This is a space where various messages generated during the verification process are collected and managed. This area provides key communication features for collaboration between Developers and Administrators.

{% tab title="(4). Scanned Component List" %}
#### (4). Scanned Component List

* Displays the list of scanned components, and you can click on each item to check the detailed information.

<div align="left"><figure><img src="../../.gitbook/assets/clarity_section_yellow_4 (1).png" alt=""><figcaption></figcaption></figure></div>



**Item Description**

* CONFLICT: Displayed in red if the component conflicts with the license policy, and in white if there are no conflicts.
* COMPONENT (COMPONENT VERSION) : Information on the component name and its version.
* COMPONENT LICENSE: License information for the component.
* OBLIGATION TYPE:  Information on the obligation type for the license (based on the project's license policy).
* USAGE TYPE : The default value is N/A; it can be specified during the Usage Type Input stage.
* DISCLOSE:  Indicates whether the component's source code is disclosed.
* MODIFICATION: Indicates whether the component has been modified.
* NOTICE: Indicates whether a notice is required for the component.
* PATENT: Indicates whether there are patents related to the component.
* VULNERABLE LEVEL: The security vulnerability grade (based on the project's security vulnerability policy).
* SEVERITY: The risk level of the vulnerability based on the CVSS score.
* SECURITY: Displays a list of CVEs (security vulnerabilities) found in the component.

#### 4. Detailed Description of the Clarity Verification Workflow

* The following explains each of the 8 stages.



**Step1 - Analyzing**

* The file scanning process is in progress in the background.
* Once the scan is complete, it automatically moves to the Request Usage Type Review stage.

<div align="left"><figure><img src="../../.gitbook/assets/image (74).png" alt="" width="563"><figcaption></figcaption></figure></div>



**Step 2 – Request Usage Type Review**

* This is the stage where the Developer requests the Administrator to allow the input of usage types
* This is the screen displayed to the Developer after the scan is complete.

<div align="left"><figure><img src="../../.gitbook/assets/image (79).png" alt="" width="563"><figcaption></figcaption></figure></div>



* The Developer can click the \[Add new comment] button to leave a comment regarding the current stage.

<div align="left"><figure><img src="../../.gitbook/assets/image (78).png" alt="" width="563"><figcaption></figcaption></figure></div>



* Enter the comment to be sent to the Administrator at this stage.

<div align="left"><figure><img src="../../.gitbook/assets/image (76).png" alt="" width="492"><figcaption></figcaption></figure></div>



* You can check the comments left for the current stage in the **Communication** section.

<div align="left"><figure><img src="../../.gitbook/assets/image (77).png" alt="" width="563"><figcaption></figcaption></figure></div>



**Step 3 – Usage Type Review**

* This is the stage where the Administrator reviews the usage type input request and either approves or rejects it.
* This stage cannot be proceeded by the Developer; only the Administrator can leave comments or move to the next stage.

<div align="left"><figure><img src="../../.gitbook/assets/image (91).png" alt="" width="563"><figcaption></figcaption></figure></div>



**Step 4 – Usage Type Input**

* This is the stage where the Developer enters the usage type.
* The Developer can leave a comment regarding the current stage.

<div align="left"><figure><img src="../../.gitbook/assets/image (92).png" alt="" width="563"><figcaption></figcaption></figure></div>



* The Developer inputs how the component is being used; depending on the selected usage type, license policy conflicts may be resolved or new conflicts may arise. ([Refer to the COMPONENT LIST description](how-to-verify-with-clarity.md#id-4-.-component-list))

<div align="left"><figure><img src="../../.gitbook/assets/image (93).png" alt="" width="563"><figcaption></figcaption></figure></div>



* You can configure exception license policy rules based on the usage type in the License Policy Rules Exception List.
* <mark style="background-color:yellow;">Policy > License Policy ></mark> <mark style="background-color:yellow;"></mark>_<mark style="background-color:yellow;">**License Policy Rules Exception List**</mark>_

<div align="left"><figure><img src="../../.gitbook/assets/image (94).png" alt="" width="563"><figcaption></figcaption></figure></div>



**Step 5 –  Review**

* This is the stage where the Administrator reviews the entered Usage Type and components with conflicts. This stage cannot be proceeded by the Developer.
* If there are no issues, move to the **Ready** state to complete the verification.
* If further review is required, instruct to perform **follow-up** actions.
* If re-verification is required, click the **Re-verify** button to perform a scan.
* If the request needs to be rejected, click the **Reject** button to return to the previous stage.

<div align="left"><figure><img src="../../.gitbook/assets/image (95).png" alt="" width="563"><figcaption></figcaption></figure></div>



* The Administrator can enter fulfillment conditions for components where conflicts have occurred.

<div align="left"><figure><img src="../../.gitbook/assets/image (97).png" alt="" width="563"><figcaption></figcaption></figure></div>



**Step 6 - Follow-up**

* This is the stage where the Developer reviews the fulfillment conditions left by the Administrator and checks whether they have been implemented.
* The Developer can leave a comment regarding the current stage.

<div align="left"><figure><img src="../../.gitbook/assets/image (135).png" alt="" width="563"><figcaption></figcaption></figure></div>



* The Developer checks the fulfillment status and completes the follow-up actions.

<div align="left"><figure><img src="../../.gitbook/assets/image (136).png" alt="" width="563"><figcaption></figcaption></figure></div>



**Step 7 - Check follow-up**

* This is the stage where the Administrator reviews the fulfillment status checked by the Developer. This stage cannot be proceeded by the Developer.
* If there are no issues, move to the **Ready** state to complete the verification.
* If re-verification is required, click the **Re-verify** button to perform a re-scan.
* If the request needs to be rejected, click the **Reject** button to return to the previous stage.

<div align="left"><figure><img src="../../.gitbook/assets/image (137).png" alt="" width="563"><figcaption></figcaption></figure></div>



**Step 8 - Ready**

* Verification Completed State
* [An SBOM can be generated based on the verification results.](how-to-verify-with-clarity.md#id-5-.-verification-report) (This is available from Step 2 onwards.)
* You can review all Communications from the entire verification process.
* Click the \[Revoke Verification] button to cancel the completed status and return to a previous state.

<div align="left"><figure><img src="../../.gitbook/assets/image (138).png" alt="" width="563"><figcaption></figcaption></figure></div>
